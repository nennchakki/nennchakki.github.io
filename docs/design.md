# 設計

## 1. 情報構造と URL

| URL | 内容 | テーマ |
|---|---|---|
| `/` | 総合トップ。作品一覧と更新記録 | noa |
| `/works/<作品>/` | 作品ページ。題名、説明、資料ごとの公開状態、固定 URL、改訂履歴 | 作品ごと（広の本は hiro） |
| `/works/hiro-string/answers/` | 解答編の目次（部・章・問題数）と、別冊の前付け（この別冊について・記号・略称） | hiro |
| `/works/hiro-string/answers/ch01/` 〜 `ch15/` | 章ごとの解答。章内目次、問題ごとの解答、前後の章への移動 | hiro |
| `/q/hiro-string/` | 印刷物の QR コードの入口。JavaScript なし、リンクだけ | 共通（テーマなし） |
| `/q/hiro-string/qr.svg`, `qr.png` | QR コード画像 | — |
| `/404.html` | 見つからない頁 | noa |

ページ内の位置にも固定の id を付けている。

- 節: `#s1-1`（節番号）
- 大問: `#p1-1`（章-問）
- 小問: `#p2-3-2`（章-問-小問。小問が 1 つだけの大問は `-q`、まとめの設問は `-sum`）
- ラベル付きの数式: `#eq-<原稿の \label>`

解答の章ページは、原稿の構成をそのまま写す: 大問の枠（題と問題番号 I-1-1）→ 共通の条件 → 小問ごとに「問題文の枠 → 考え方 → 解いてみる → □」。
別冊の「この別冊について」が、この順で読むよう指示しているため、順序を変えない。

まだ公開していない資料（正誤表、補足資料、PDF）は、作品ページで「準備中」と表示し、リンクを張らない。
公開日・頒布イベントは決まっていないので「未定」と表示している（`work.json` の `null`）。

## 2. 作品ごとのデザインの分け方

- すべてのページの `<body>` に `data-theme` を付け、テーマの CSS は `body[data-theme="…"]` の範囲だけに効く書き方にした。
- テーマの CSS は作品ごとに別のファイル（`static/assets/css/themes/<theme>.css`）で、そのテーマのページだけが読み込む。ほかの作品のページはそのファイルを読まないので、書き換えても影響しない。
- 共通の部品（ヘッダー、フッター、解答の組版 `answers.css`）は、色を CSS 変数で受け取る。

## 3b. 寄稿作品（`/writings/`）

合同誌に寄稿した作品の一覧（2026-11-09 追加）。トップの「寄稿作品」には題名・収録先・頒布・一覧用の紹介文だけを置き、詳細はこのページに置く。ノアのテーマのまま、作品一覧と同じ台帳の組み方にした。

- データは三つに分けた。合同誌（`anthologies.json` の `books`）、頒布の機会（各 book の `distributions`。イベント・日付・配置・状態）、寄稿作品（`works.json`）。一冊の合同誌が複数の場で頒布されることがあるため（例: 篠澤広科学哲学合同は文学フリマ東京43と GSF04）。
- 1 作品の項目: 題名、収録先とサークル、一覧用の紹介文、詳しい紹介文、登場人物、主題、頒布（状態・イベント・日付・配置）、章立て、前作、告知（本人と主催の X のポスト）。
- 題名・章立て・登場人物・主題は、原稿の生データを読んで確かめた（照合用の下書きにあった誤りは採らなかった。例: 主題の術語が原稿にない、登場人物の抜け、章立ての違い）。紹介文は、結末や謎の答えを書かない。
- 頒布日は、告知で確かめられたものだけを書く。C109 の会期（3日間）を合同誌ごとの頒布日として書かない。地学・地理合同誌は、主催の配置の告知がまだないので「日付は未告知」「配置は未告知」と出す。
- 本文・PDF は配らない。

## 5. 技術選定

| 候補 | 判断 |
|---|---|
| Astro | 作品ごとのレイアウトは組みやすい。ただ、変換の中心は TeX の解釈で、Astro の機能はほとんど使わない。依存が数百パッケージ増える |
| Pandoc | 単一ファイルの LaTeX は読めるが、この原稿の構造マクロ（`\solutionpart` の 4 引数、`\begingroup` 内のマクロ再定義、`\pretocmd`）を解釈しない。読めない命令を黙って捨てることがあり、欠落を検知しにくい。手元に未インストール |
| LaTeXML | マクロを TeX に近い形で処理できるが、luatexja・jlreq・tcolorbox の対応が不完全で、日本語の和文処理の再現に手間がかかる。手元に未インストール |
| 専用の変換器（採用） | 数式の外で使う命令は、見出し・枠・表・リスト・書式の数十種類に限られている。その一覧を変換器に持たせ、知らない命令に出会ったら行番号を出して止める。数式は中身を書き換えずに KaTeX へ渡す |

採用した構成:

- Node.js のスクリプトで静的な HTML を出す（フレームワークなし）。依存は KaTeX 0.16.47 と qrcode 1.5.4 の 2 つ（テストに jsQR と pngjs）。版は固定した。
- 数式は、ビルドのときに KaTeX で HTML と MathML に組む。ブラウザで JavaScript を動かさなくても数式が表示される。数式をコピーすると TeX の原文が取れる（KaTeX の copy-tex）。
- 横に長い数式は、その数式の枠だけ横にスクロールする（式を縮めたり折り返したりしない）。はみ出す枠には、キーボードで操作できるよう `tabindex` を付ける。
- 図は、原稿のプリアンブルのまま LuaLaTeX で組んで SVG にした。

## 6. データの流れ

```
原稿ディレクトリ（手元だけ）
  └─ npm run snapshot ──→ content/<作品>/answers/
                             source/answers.tex（別冊解答のコピー）
                             manifest.json（ハッシュ・数・本文との照合）
                             figures/*.svg
CI / 手元
  content/ ── npm run build ──→ dist/ ── npm test ──→ GitHub Pages
```

- 原稿ディレクトリは読むだけで、書き込まない（スナップショットの作成中に原稿が変わったら止まる）。
- 本文の TeX、作業メモ、バックアップ、中間ファイルはコピーしない。`dist/` に TeX・Markdown・JSON などが入っていないことを `npm test` が確かめる。
- ローカルの絶対パスは `manifest.json` にも HTML にも書かない（ファイル名だけ）。
- 公開した HTML を手で直さない。表示の修正は変換器（`tools/`）と CSS で行う。
